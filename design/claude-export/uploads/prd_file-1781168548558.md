# Karaoke PRD v2 — React UX, Item Page & Lyrics

Successor scope to [[karaoke-prd|Karaoke PRD (v1)]]. **v1 is shipped and live** (`BeFeast/karaoke`, devbox `:13140`): URL → RunPod GPU → `vocals.mp3` + `karaoke.mp3` + `lyrics.txt` on NFS, a Submitter SPA (`/app`, Vite+React, Scribe "field" design), job-management actions (cancel / retry / remove / clear-failed, PRs #49/#51/#52), and a Scribe-styled server-rendered result page.

This PRD covers what v1 deliberately left thin. Three pillars:

- **A. A real front-end.** Promote the SPA to the product surface and make the **item/result page a first-class React route** with a proper experience — not a static server-rendered page.
- **B. The item page & a real player.** Waveform, seek, vocal↔instrumental control, **Download**, **Share**, and a **synced-lyrics** view.
- **C. A lyrics overhaul.** Whisper-ASR-on-vocals is poor for songs. Use the YouTube **metadata** (artist/track) to fetch **real, time-synced** lyrics from external services, with ASR as a fallback.

> **Auth note (unchanged from v1 operator decision):** the app runs trusted-LAN, Clerk dormant. "Share" today means *copy the unlisted link*; real per-user sharing is a later milestone gated on Clerk. This PRD does **not** turn on auth.

## 1. Why now

- v1 proved the pipeline and gave us a clean design system + API. The UX is still a thin dashboard + a read-only result page.
- The operator's explicit asks: (1) rewrite the UI/UX as a proper Vite+React app with much more functionality; on the **item page** specifically — **Download, Share, a real player**; (2) **lyrics quality is unacceptable** — Whisper on song vocals mangles words; we have metadata, so look the real lyrics up online (there are dedicated lyrics services).

## 2. Goals / non-goals

### Goals

- A cohesive **Vite+React** front-end: dashboard + a rich **item route** (`/app/job/:token`) replacing the server-rendered `/share` page as the primary experience.
- A **real audio player**: waveform + scrub, play/pause/seek/keyboard, switch/blend **instrumental ↔ vocals**, loop / A–B repeat, playback-rate, and time-**synced lyrics** highlighting.
- **Download** (per-file: instrumental / vocals / lyrics; and "download all" as a zip) and **Share** (copy unlisted link now; share-with-user later).
- **Real lyrics**: fetch synced (LRC) lyrics by metadata from external services; fall back to Whisper ASR; optionally **force-align** plain lyrics to the vocal stem for timing.
- Keep the design system (Scribe "field"), keep LAN-mode, keep the existing API contract additive (no breaking changes).

### Non-goals (this phase)

- Turning on Clerk auth / real multi-user sharing (separate, later).
- Pitch/key shifting, tempo change, multi-stem (>2) separation (v3 candidates).
- A native mobile app (responsive web only).
- Replacing the backend pipeline/runtime (RunPod path stays as-is).

## 3. Pillar A — Front-end architecture

**Decision (proposed): the item page becomes a React route, with a minimal server-rendered fallback retained for raw/no-JS link opens.**

- Today `/share/{token}` is server-rendered HTML (now Scribe-styled). It works without JS — good for a link someone opens cold. But it can't host a real player/synced-lyrics UX.
- Proposal: add a React route **`/app/job/:token`** that fetches the job + artifacts + lyrics and renders the full player. The dashboard's `▶ Open` and the "Share" link point here.
- Keep a **slimmed** `/share/{token}` server-rendered page as a graceful fallback (and the canonical URL for eventual external/SEO/unauth opens) that links to the React route — so a shared link never shows a blank page if JS is blocked.
- The SPA stays at `/app` (Vite, `base: "/app/"`), client-side routed (a tiny hash/path router; no new heavy router dep unless justified). Build still baked into the image via the `oven/bun` stage.

Open question O1 (below) is whether to keep the SSR fallback or go React-only.

## 4. Pillar B — Item page & the player

### 4.1 Layout (item route)

- Header: title, source `↗`, status chip, owner/date, **Download ▾** + **Share** + **Remove** actions (reuse the confirm modal).
- **Player** (the centerpiece) — see 4.2.
- **Lyrics** panel beside/below the player — see Pillar C; synced highlight when timed lyrics exist, plain scroll otherwise.
- Metadata strip: detected artist/track, duration, model/provider provenance, RunPod cost.

### 4.2 Player requirements

- **Waveform + scrub** via [wavesurfer.js](https://wavesurfer.xyz/) (mature, MIT, regions/timeline plugins). Renders the instrumental by default.
- **Two stems, one transport.** Load `karaoke.mp3` (instrumental) and `vocals.mp3` and keep them sample-synced. Controls:
  - a **balance/crossfade** slider (instrumental ⇄ vocals) — practice with more/less guide vocal; **or** a simple A/B toggle. (Proposed: a vocal-level slider 0–100% over the instrumental — the karaoke-practice sweet spot.)
  - Implementation: two `<audio>`/WebAudio sources through a `GainNode` each, common transport; wavesurfer drives the visual + seek.
- **Transport:** play/pause (space), ±5 s (←/→), seek by clicking waveform/lyrics line, playback-rate (0.5–1.5×), **loop / A–B repeat** (set in/out for drilling a section).
- **Synced lyrics:** active line highlighted + auto-scroll; click a line to seek. Falls back to a plain scroll box when only plain lyrics exist.
- **Download ▾:** instrumental, vocals, lyrics (`.lrc` if synced else `.txt`), and **Download all (.zip)**.
- **Share:** copy the unlisted link (toast). Later (auth): "share with user".
- **Responsive:** stacks on mobile; waveform shrinks; lyrics below; large touch targets.
- **Accessibility:** keyboard transport, ARIA on controls, respects reduced-motion.

### 4.3 Backend support needed

- `JobOut` (and/or a job-detail endpoint) should expose the **artifact list** (which of instrumental/vocals/lyrics/metadata exist + sizes) so the player only offers what's ready. (Today the SPA infers a fixed set; make it explicit.)
- A **lyrics endpoint** returning structured lyrics: `{ synced: bool, lrc?: string, lines: [{t, text}] | null, plain?: string, source }`.
- A **download-all** zip endpoint (or client-side zip of the three files).
- All artifact/result links stay **same-origin relative** (`/share/{token}/…`) — the public base 401s on LAN (learned in #51).

## 5. Pillar C — Lyrics overhaul

> Grounded by research 2026-06-01 (LRCLIB schema + Musixmatch/Genius terms + aligners verified live).

### 5.1 Problem

Whisper ASR on the separated vocal stem mis-hears lyrics (homophones, ad-libs, backing vocals, non-English), so `lyrics.txt` is unreliable and **untimed** — useless for a karaoke highlight.

### 5.2 Strategy: metadata → real lyrics, synced if possible

1. **Extract metadata** we already have. `yt-dlp` exposes `artist`, `track`, `album`, `title`, `duration` (YouTube Music & many music videos populate `artist`/`track`; otherwise parse `"Artist - Title"` from `title`). Persist these on the job.
2. **Look up synced lyrics by metadata** from an external lyrics service (see provider table — **LRCLIB** is the leading free/no-key/synced-LRC candidate), matched on artist + track (+ album + duration for disambiguation). Prefer **synced (LRC)**; accept plain if that's all there is.
3. **Fallbacks, in order:** provider A (synced) → provider B → YouTube captions/subtitles (`yt-dlp --write-subs/--write-auto-subs`, if present) → **Whisper ASR** (current behavior) as the last resort.
4. **Timing when only plain text exists:** optionally **force-align** the known lyrics to the clean **vocal stem** (we already have it from Demucs) to synthesize per-line/word timestamps — turning correct-but-untimed lyrics into karaoke-synced lyrics.
5. **Provenance:** record `lyrics_source` (`lrclib_synced` | `lrclib_plain` | `provider_x` | `yt_captions` | `whisper_asr` | `forced_aligned`) + `synced: bool` in `metadata.json` so the UI and we know what we're showing.

### 5.5 Recommended sourcing chain (grounded)

1. **LRCLIB `/api/get`** (artist+track+album+**duration**) → if `syncedLyrics`, done (best case).
2. **LRCLIB `/api/search`** fuzzy → best title/duration match → `syncedLyrics` else `plainLyrics`.
3. Plain only (LRCLIB plain / lyrics.ovh) → **force-align** (ctc-forced-aligner; WhisperX alt) against the vocal stem → synthesize LRC.
4. No external match → **Whisper ASR** on the vocal stem (current) as the floor.
5. Respect LRCLIB `instrumental: true` → skip lyrics, mark the track instrumental.
6. **Cache aggressively** (per artist+track+duration); consider **self-hosting LRCLIB** to drop the external dependency + SLA risk.

#### 5.6 Musixmatch deep-dive (operator asked, O7)

Musixmatch has the best synced/word-level data in the market, but its terms make it a poor fit for a free homelab tool:

- **Free "Developer" plan:** ~**2,000 calls/day**, requires an API key, but returns only a **~30 % snippet of *plain* lyrics** — **no full lyrics and no synced lyrics**. So the free official tier gives us *nothing usable* for karaoke (no timing, partial text).
- **Synced is premium-only.** Line-level (`track.subtitle.get`) and word-level karaoke (`track.richsync.get`, "select catalog tracks") sit behind a **Commercial** plan — custom/sales-negotiated pricing (reported ≈ **$0.005–0.02/call**, est. **$500–1,500/mo** at app scale), with a **mandatory attribution link** on every lyrics view and key-revocation/contractual-damages risk for ToS breaches.
- **The "free synced" path that open karaoke tools actually use is unofficial:** libraries like `syncedlyrics` reach Musixmatch via a **reverse-engineered mobile token** to pull synced lyrics for free. This **violates Musixmatch ToS**, is fragile (token rotation breaks it), and is *legally worse* than LRCLIB — so we **decline** it as a default. (It could be an operator-opt-in experimental fallback, but it buys little over LRCLIB.)

**Verdict:** Musixmatch stays **excluded** for now. Its only legitimate synced access is a commercial contract — overkill for a LAN-internal tool — and its free tier is useless for our purpose. **Revisit only if** (a) we ever take this public/commercial *and* (b) LRCLIB's coverage proves insufficient in practice; at that point a Commercial Musixmatch plan (richsync word-level) would be the quality ceiling. Until then: **LRCLIB synced → force-align → ASR** already gives us free, real, timed lyrics without the licensing/ToS entanglement.

## 5.4 Storage / format

- Store `lyrics.lrc` (synced) and/or `lyrics.txt` (plain) under the job's `exports/`; surface both. LRC = `[mm:ss.xx] line` tags the player parses to highlight the current line.
- New artifact kinds: `lyrics_lrc`. Keep `lyrics` (plain) for compatibility.

## 6. API additions (additive, non-breaking)

- `GET /jobs/{id}` (or extend `JobOut`) → include `artifacts: [{kind, name, size}]`, detected `artist`/`track`, `lyrics_source`, `synced`.
- `GET /share/{token}/lyrics` → structured lyrics JSON (`{synced, lrc?, lines?, plain?, source}`).
- `GET /share/{token}/lyrics.lrc` → add to the artifact allowlist alongside `lyrics.txt`.
- `GET /share/{token}/all.zip` → bundle (or do client-side).
- (Later, auth) share-grant endpoints.

## 7. New-functionality backlog (beyond the player)

- Dashboard: client-side **search/filter** by title/status, sort, relative timestamps (needs `created_at` in `JobOut`).
- **Re-transcribe / re-fetch lyrics** action on an existing job (try a different provider / force-align) without re-running separation.
- Submit options: lyrics mode (auto / synced-only / ASR-only), manual artist/track override when detection is wrong.
- Toasts for actions (copy link, deletes), and a real "copied!" affordance.
- WebSocket `/ws` wired into the SPA for live progress (replaces 3 s polling, #8).
- Optional: lightweight `og:`/oEmbed meta on the SSR share page for nice link unfurls.

## 10. Risks

- **Lyrics match rate / wrong matches.** Metadata is often messy (`"Artist - Title (Official Video) [4K]"`); bad parse → wrong or missing lyrics. Mitigate with duration matching + a manual artist/track override + clear provenance + ASR fallback.
- **Licensing.** Lyrics are copyrighted; provider ToS may limit redistribution/caching. LAN-internal use is low-risk, but record the source and respect provider terms; revisit before any public exposure.
- **Synced-lyrics availability** is far lower than plain; many tracks have none → forced alignment or plain fallback.
- **Player complexity** (two sample-synced stems + waveform + seek) is fiddly across browsers; budget for Safari/Helium testing via the CDP harness ([[prisma-cdp-screenshot-harness]]).
- **Front-end dep weight** (wavesurfer + zip) — keep the bundle lean; lazy-load the player route.
